Hiểu sâu Multi-Memory Agent với Zep

1. Bức tranh lớn

Một chatbot chỉ nhìn thấy prompt hiện tại. Một memory agent phải quyết định thông tin nào cần lấy lại, lấy từ đâu, giữ bao nhiêu và đưa vào context theo thứ tự nào.

Người dùng
query mới
Router
xác định layer
Retrieve
tìm evidence
Assemble
trim theo budget
Agent
trả lời có căn cứ
query → route → retrieve từng layer → budget/priority → merged context → answer
Ý tưởng cốt lõi: Memory không phải một “kho chat khổng lồ”. Memory là một pipeline chọn lọc evidence. Retrieval sai thì model có thể nói rất trôi chảy nhưng vẫn sai sự thật.

2. Bốn loại memory

Hãy phân loại theo câu hỏi mà người dùng đang hỏi, không chỉ theo nơi lưu dữ liệu.

SHORT-TERM

Working / current conversation

Dùng cho “vừa nói gì?”, đại từ “nó” đang chỉ gì, hoặc các turn gần nhất. Nhanh nhưng bị giới hạn context.

Ví dụ: E01, E10.

LONG-TERM

Facts và preferences bền vững

Dùng cho “tôi thích gì?”, “project đang dùng stack nào?”, open loop và deadline qua nhiều session.

Ví dụ: E02, E03, E08, E09.

EPISODIC

Trajectory và kinh nghiệm

Dùng cho “lần trước đã thử gì?”, “cách fix nào hiệu quả?”, outcome và reflection có provenance.

Ví dụ: E04, E05.

SEMANTIC

Domain knowledge dùng chung

Dùng cho policy, playbook, tài liệu và quy tắc không thuộc riêng user nào.

Ví dụ: E06, E11.

Câu hỏiLayer phù hợpNamespace
“Deadline review vừa nói là khi nào?”Short-termLocal session
“Minh thích ngôn ngữ nào?”Long-termTheo user
“Lần trước fix timeout ra sao?”EpisodicTheo user

3. Zep Cloud V3: user graph và semantic graph

Lab dùng Zep Cloud V3. Trong V3, conversation được gọi là thread. Có hai không gian dữ liệu quan trọng.

User-scoped graph

Chứa memory của một user: facts, preferences, episodes và context liên quan. Long-term/episodic phải tìm bằng user_id để tránh data leak.

user.add
thread.create(user_id=...)
thread.add_messages(...)
thread.get_user_context(thread_id=...)

Standalone semantic graph

Chứa knowledge dùng chung như payment policy hoặc incident playbook. Semantic retrieval phải tìm bằng graph_id, không phải user.

graph.search(
  graph_id="vinuni-lab17-domain-kb",
  scope="episodes"
)
Vì sao semantic dùng scope=episodes? Trong lab, raw document episode giữ literal marker như PAYMENT-RULE-3 và CONN-POOL-FIRST. Scope auto có thể trả fact đã trích xuất nhưng làm mất marker mà evaluator cần kiểm tra.

4. Short-term memory và compaction

Buffer

Giữ toàn bộ messages. Đơn giản và chính xác, nhưng token tăng tuyến tính.

Summary

Nén các turn cũ thành summary. Tiết kiệm token nhưng có nguy cơ mất chi tiết.

Sliding window

Giữ summary/durable notes và K turn gần nhất. Đây là chiến lược mặc định của lab.

old turns ──compaction──> summary + durable notes
                                  + recent K turns

Compaction tốt không phải là tóm tắt văn hoa. Nó phải ưu tiên:

  • state hiện tại
  • decision đã chốt
  • TODO/open loop
  • constraint và deadline

Trong E10, thông tin REVIEW-DEADLINE-1600, ngày Friday và thời gian 16:00 phải sống sót sau khi raw transcript bị loại khỏi cửa sổ gần nhất.

5. Đọc bốn hàm student

Mỗi hàm có một trách nhiệm hẹp. Tách retrieval theo layer giúp dễ debug và đo lường.

Long-term

Prime thread bằng query để Zep biết relevance, sau đó lấy Context Block bằng thread.get_user_context. Trả về chuỗi .context, không trả object.

Episodic

Gọi graph.search(user_id=..., scope="episodes"). Render content và provenance; giữ các reflection marker.

Semantic

Gọi graph.search(graph_id=..., scope="episodes"); nếu SDK không hỗ trợ thì fallback sang nodes.

Assemble

Không nối chuỗi thủ công tùy tiện. Dùng ContextBudgetManager.assemble(layers) để áp dụng giới hạn và priority.

Giới hạn query: Zep graph search không nhận query quá 400 ký tự. Vì vậy mọi query trước khi search cần đi qua cap_query(query).

6. Context budget: ít nhưng đúng

Với LAB_CONTEXT_TOKENS=8000, lab phân bổ 20% context memory theo tỉ lệ 10/4/3/3.

short_term → long_term → episodic → semantic

Thứ tự này phản ánh nguyên tắc: context gần người dùng nhất và có tính hội thoại cao nhất được ưu tiên trước; knowledge chung chỉ được thêm khi còn budget.

7. Benchmark: đánh giá evidence, không đánh giá văn phong

  • Có marker bị cấm trong must_not_contain không?

8. Hai vấn đề khó: conflict và mixed context

Recency wins — E08

Khi user từng chọn backend cũ rồi cập nhật preference mới, không nên xóa lịch sử. Hãy giữ validity range/provenance, nhưng khi trả lời hiện tại phải ưu tiên fact mới: TypeScript + NestJS cho BLUEBIRD-42.

Mixed retrieval — E07

Một query có thể cần cả preference user và rule domain. Long-term cung cấp Python; semantic cung cấp Idempotency-Key. Không layer nào một mình đủ evidence.

Tự hỏi: tại sao không đưa toàn bộ transcript vào prompt?

Vì transcript chứa nhiễu, facts cũ, mâu thuẫn và nhiều token. Prompt dài hơn cũng làm model khó chú ý evidence quan trọng. Memory system phải làm công việc chọn lọc trước khi model trả lời.

Semantic graph dùng chung không bị xóa khi quên một user, vì nó là domain knowledge không thuộc user đó. Ngược lại, user graph và Redis keys của user phải biến mất.

# Redis user keys remaining: 0

10. Lộ trình học và tự kiểm tra

  1. Đọc data/sessions.json và tìm marker của E01–E11.
  2. Chạy smoke, seed và short-term demo.
  3. Hoàn thiện retrieval từng layer, kiểm tra bằng --only-layer.
  4. Chạy full benchmark và so sánh no-memory.
  5. Giải thích E08 recency, E09 isolation, E10 compaction, E07 mixed.
  6. Chạy privacy drill sau khi đã lưu report.
  7. Nếu có golden set, chỉ nhận bonus khi đạt 20/20.

Bài tập suy nghĩ

Nếu query là “Lần trước payment retry bị lỗi vì sao, và theo policy hiện tại nên retry thế nào?”, bạn sẽ route vào layer nào?

Đáp án gợi ý

Episodic để lấy nguyên nhân/outcome lần trước; semantic để lấy policy hiện tại. Nếu user còn có preference coding language thì thêm long-term. Cuối cùng assemble theo budget.

Checklist hoàn thành

  • Student benchmark đạt ít nhất 9/11, hiện tại là 11/11.
  • Không leak memory giữa hai user.
  • Context được trim theo 10/4/3/3.
  • Report có evidence, latency và token reduction.
  • Privacy có delete và verify.
  • Không commit API key hoặc golden file.
